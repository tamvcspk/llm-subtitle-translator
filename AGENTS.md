# Project Collaboration Rules

## Fork Status

This repository is `tamvcspk/llm-subtitle-translator`, a fork of `kingzleshe/gemini-srt-translator-bazarr` (remote `upstream`, push disabled). The fork is being redesigned; the target design lives in `docs/design/SPEC.md` and `docs/design/ARCHITECTURE.md` and takes precedence over upstream docs when they conflict. `docs/ARCHITECTURE.md` describes the inherited (current) code.

- Pull upstream fixes by cherry-pick only; never push to `upstream`.

## Runtime Environment

- Deployment target for this fork is not set up yet. The upstream author's host details (`192.168.1.1`, SSH as root) do not apply to this fork; do not connect to them.
- Default container paths: `/state`, `/media`, web port `6789`. `/queue` is only read once at start-up to settle an older queue (P10); there is no `/bazarr-postprocess` any more.

## Build and Deployment

- Images are built through GitHub. The default scope is to modify repository code, run relevant tests, and report results; do not build images locally or on the remote device.
- Use read-only SSH checks when the live service state is needed. A code change request does not authorize deployment. Modify container files, replace remote scripts, or restart or recreate containers only when the user explicitly requests an update to the running service.
- Deploy using images built through GitHub. If the user explicitly requests a temporary direct container modification, back up the affected files first and explain that a normal restart preserves the changes, while recreating the container from an image overwrites changes made inside the container.
- Clearly distinguish repository code changes, completed GitHub image builds, and running container updates in reports. Claim only states that have been verified.

## Development Commands

The repo is a **uv workspace** (virtual root, one `uv.lock`): `apps/server` (`llm-subtitle-server`: `worker.py`, `subserver/`, `tests/`, not packaged) and `packages/subcore` (`subcore` engine library, `src/` layout). Install with `uv sync --locked --all-packages`; add deps with `uv add --package <member> <dep>`. Tests use stdlib `unittest`, not pytest; each member's tests run in a separate process. CI (`.github/workflows/ci.yml`) runs:

```bash
uv run --locked python -m unittest discover -s apps/server/tests -t apps/server -v
uv run --locked python -m unittest discover -s packages/subcore/tests -t packages/subcore -v
uv run --locked python -m compileall -q -f apps/server/worker.py apps/server/subserver packages/subcore/src
uv run --locked subcore --help
```

Run one module or test by dotted name (from the member directory):

```bash
uv run --locked --directory apps/server python -m unittest tests.test_worker_queue
uv run --locked --directory apps/server python -m unittest tests.test_worker_queue.TestWorkerQueueTests.test_enqueue_translation_jobs_for_enabled_targets
```

The Docker image installs only `llm-subtitle-server` (which depends on `subcore`, so `packages/subcore/src` and its README are copied too) and keeps the old runtime layout (`/app/worker.py`, `/app/subserver`, `/app/static`). Every new workspace member needs its `pyproject.toml` copied in the `Dockerfile` before `uv sync --locked`.

Local console preview on Windows: `scripts/start-local.ps1 [-Demo] [-NoWorker]` runs against an isolated `local-state/` directory instead of the Docker `/state` and `/queue` mounts. `-NoWorker` keeps the process from consuming queue jobs.

Trying a change in the browser with real rows and no key: `scripts/preview.ps1 [-Reset] [-Rebuild]` seeds `local-state/preview` (`apps/server/tests/preview_seed.py`, a fake provider, no Bazarr), builds `apps/web` when it is stale and serves the console on `127.0.0.1:6790` with `--no-worker`. `node scripts/smoke/smoke.mjs [--routes ...] [--steps file.mjs]` walks it in Edge through `playwright-core` (installed on first use into the git-ignored `local-state/tools`, not a project dependency) and fails on a blank page, a console error or a failed `/api` call; `scripts/smoke/steps/` holds the clicks of one change. Testing is split over two sessions through one file, `local-state/handoff/TEST-PLAN.md` (git-ignored): the heavy session writes a short plain-language plan after a change (`test-plan` skill, "viết kịch bản test") and later reads the findings ("đọc kết quả test"); a light session drives the real app in a browser tool when the user says "test" (`web-test` skill), writes only the Findings section and never edits code. `scripts/preview.ps1 -Bazarr` (not with `-Live`) adds a stand-in Bazarr (`scripts/fake_bazarr.py` on `127.0.0.1:6791`; `/__fake/shrink` and `/__fake/restore` in a browser tab make it answer with a much smaller library or the full one), runs the catalog sync loop and leaves an older worker's `queue/` folders for the start-up to settle (`preview_seed.py --old-queue`); the worker runs with `--no-queue`, so nothing can call a model. `scripts/preview.ps1 -Live` runs the real worker with a real Gemini key (put it alone in `local-state/secrets/gemini.key`, git-ignored, or set `GEMINI_API_KEY`; `-MaxCallsPerDay` is a hard cap, default 1000 (free tier: Flash 10K a day, Flash Lite 150K), and `-MaxCallsPerJob` one per job, default 20; every task runs on `-LightModel` (default `gemini-3.1-flash-lite`) and only the fallback layer and the judge on `-StrongModel` (default `gemini-3.8-flash`; pick models with free-tier quota on the key's project, `gemini-3.5-flash` has none); `suggest_from_facts` is off; these are read on the first run of a state, so use `-Reset`; no episode is pre-translated; no Bazarr; `GST_ONLY_PATHS` confines it to the demo media); the plan's "Money" section lists the only actions allowed to call the model. The tester drives the console through the project's Playwright MCP server (`.mcp.json`, `@playwright/mcp` pinned, Edge, headed so the user can watch, 820x1180, screenshots and snapshots in `local-state/pw/`; approved for the project in `.claude/settings.json`) with full freedom on the disposable preview data: events, screenshots, console, network, resizing. `smoke.mjs --steps` (Playwright modules in `scripts/smoke/steps/`) is optional and no longer part of the plan. Without `-Live` nothing that calls the model can be tried, and Bazarr never can.

`subcore` has a declarative CLI for judging translation quality without the worker (it knows no DB, queue or HTTP): `uv run subcore translate file.srt --glossary g.yaml` (key from `GEMINI_API_KEY` (`OPENAI_COMPAT_API_KEY` for `openai_compat`; a key never crosses providers), or `--api-key-file`; `--provider fake` for a dry run), plus `bundle` (write the bundle of a translation), `render-prompt` (print the requests, no call), `validate` (review a translation against its source) and `compare` (two bundles, or one against a golden set). Every translating command works from a bundle (`--bundle`); flags win over it.

## Which test is meant

- **Unit tests** (Python `unittest`, web `vitest`) are part of every change and phase: written with the code, in the same diff, never a separate request. A change without them is not done.
- **"viết test", "test case", "kịch bản test"** from the user means the browser hand-off: use the `test-plan` skill (write `local-state/handoff/TEST-PLAN.md`, then the light session runs `/web-test`). It does not mean "write more unit tests".
- **"test" / "test web"** typed in the light session is the `web-test` skill; "đọc kết quả test" in the heavy session is `test-plan` part B.

## Architecture

Read `docs/ARCHITECTURE.md` before changing queue, translation, or Bazarr behavior; it is the source of truth for module responsibilities, queue layout, and job shape. Domain vocabulary (translation job, translation attempt, translation version, daily quota pause, queue lifecycle) is defined in `CONTEXT.md`; use those terms in code and reports. HTTP endpoints are in `docs/API.md`, settings in `docs/CONFIGURATION.md`.

The end-to-end flow spans three independent pieces (Bazarr pushes nothing, ADR-10):

1. The worker **pulls** the library from Bazarr's API into the catalog cache (`catalog.py`, `MediaLibrary.catalog()`), and makes jobs only when the admin requests translations in Library (`job_requests.py`) or the `auto_request` policy asks (`auto_request.py`).
2. `apps/server/worker.py` + `subserver/` consume the queue one job at a time, translate in-process with `subcore`, write the target `.srt` beside the media, and ask Bazarr to rescan.
3. `apps/web` is the web console (React, Vite, Mantine; ADR-17): it talks only to the worker's own API, and the worker serves its build. See "Frontend" above.

`packages/subcore` must stay free of Bazarr, queue, and HTTP knowledge (ADR-2); the worker depends on it, never the reverse. Roadmap phases (P0–P16, including P0b–P0d), their checklists, and status are in `PLAN.md`; tick items there as work lands.

Seams to respect when adding code:

- `RuntimeContext` (`subserver/runtime.py`) is the composition seam for the running process. New runtime wiring depends on its typed fields; the legacy module-level functions are compatibility entry points for older callers and tests.
- `queue_policy.py` holds pure scheduling, breaker and quota decisions; state changes stay in `jobs.py` (`JobStore`, SQLite) and the lifecycle in `queue.py` (`JobQueue`). The HTTP layer reaches the queue only through `ConsoleActions` (and the Library's requests through `CatalogActions`). The old queue folders enter the table once, at start-up, only through `intake.py`.
- `TranslationAttempt` (`translation_attempt.py`) is the only place that translates through `subcore`; the typed provider errors (`QuotaExhausted`, `RateLimited`/`Unavailable`, ...) become the queue's `DailyQuotaExceededError` / `ProviderUnavailableError` only in `provider_guard.mapped_errors`, which every kind of job uses (never classify failures by parsing error text). An attempt refuses a variant when it has no version history or no library, and masks the free text (overview, title, story sections) before the bundle is gathered. Progress reaches the queue through the status callback (`progress_done`/`progress_total`).
- `subserver/` is five layer packages (ADR-18, P15c): `domain/` (pure decisions and the port types: `ports`, `config`, `queue_policy`, `rules`, `gather`, ...), `services/` (the use cases: `units`, `console`, `library`, `versions`, `suggestions`, ...), `jobs/` (`JobStore`, `JobQueue`, `provider_guard`, the handlers that run a job), `adapters/` (Bazarr, TMDB, HTTP client, providers, `settings`, `logs`, `telemetry`, and the `store/` package) and `api/` (the HTTP handler `web.py` and the `*_api` routers); `runtime.py` stays at the top. `tests/test_core_boundary.py` enforces the direction: `domain` imports only `subcore` and the standard library; `services` and `jobs` import `domain`, each other, the `Store` and the `Telemetry` sink, never another adapter, `api`, a socket or an HTTP client; `adapters` never import a use case or `api`; `api` never imports the `Store`, `JobQueue` or `JobStore` (a route asks a service). A new module goes in exactly one layer (the test fails for one outside them) and docs/ARCHITECTURE.md says which goes where. There are no alias modules at the old flat paths.
- Core modules reach Bazarr and TMDB only through the `MediaLibrary` and `Metadata` ports (`domain/ports.py`); `worker.py` builds the adapters (`BazarrMedia`, `TmdbMetadata`) and passes them down. Enforced by `tests/test_core_boundary.py`, which also keeps `worker.py` (the composition root) free of direct socket and HTTP-server imports. The console is a FastAPI app served by uvicorn in this process (ADR-18, P15d): `api/web.py` builds it (`create_app`) and runs it (`start_web_server`), `api/security.py` is the auth gate, `api/auth_api.py` and `api/console_api.py` are the routes that are not a page's own, and each page router (`api/*_api.py`, among them `keys_api.py`) keeps its regex table and pure `handle` and puts it on the app with `register` (`common.add_table_routes`). The settings and API keys service (`SettingsService`) is in `adapters/settings.py`. A route only parses, calls a use case (`ConsoleActions`, `UnitService`) and formats the answer, so queue and job-building logic goes in `services/console.py`, not in a route; synchronous work runs on the thread pool through `common.blocking`, never on the event loop. A new route is a row of a table or a function in `console_api.py`, and a line in `docs/API.md`. A body has a model in `api/schemas.py` (unknown fields pass; a flag that makes a call spend is `StrictBool`; a body no model names is `RequestObject`, which the use case validates). Tests serve the app with `tests/web_harness.py` (`serve_console`: uvicorn on a loopback port) or `starlette.testclient.TestClient`. Upstream cherry-picks that touch the handler in `worker.py` must be re-applied to the matching route in `api/`.
- `Store` (`adapters/store/`) is a facade over one mixin per group of tables (`auth`, `bundles`, `settings`, `records`, `insights`, `versions`, `library`, `glossary`, `suggestions`, `catalog`, `memory`), the connection and migrations being in `base.py` and `migrations.py`: a new `Store` method goes in the file of the table it reads or writes, never in `__init__.py`, and returns a named type (`test_core_boundary.py` scans every file of the package).
- Target subtitles are published only through `TranslationVersions` (`versions.py`), which records each version in the SQLite `Store` and keeps a copy under `DATA_DIR/backups/subtitles/`. An automatic job never overwrites an existing target; retranslate and revert back up a non-system file first.
- The model provider is a setting (`llm_provider`: `gemini` or `openai_compat`, with `llm_base_url`), not a property of a key. `LiveProviderFactory` (`llm.py`) rebuilds the provider chain at every call from the stored keys of that provider, so a change is live; `subcore.providers.openai_compat` is standard library only, never follows redirects and degrades structured output by capability (schema, JSON mode, prompt only) while the engine's validator stays the judge. Which model a task runs on is `config.model_for_task` (pure); new code asks it, never reads `memory_model` and friends itself.
- The application's own SQLite is not behind a port (ADR-12): core code takes `Store` (and `JobStore`) directly, and tests run it on `Store(":memory:")` with the real migrations instead of writing a fake. Ports stay only for what the project does not own (`MediaLibrary`, `Metadata`, `ProviderFactory`) and the `Telemetry` sink. A new `Store` method returns a named type from `ports.py`, never a `dict` or `sqlite3.Row` (`test_core_boundary.py` checks it).
- `subcore.matching` is the only place that decides whether a line mentions a name (glossary filter per request, character cards present, locked-term check, console matches); a test fails if another module writes a word-boundary pattern. A request is composed only by `engine.compose_request` (for `run` and `render_requests`). A bundle's `params.model` empty and `max_output_tokens` 0 mean "decided by the provider that runs it": they are neither serialised nor hashed (the CLI never fills them from a provider); the worker always sets both.
- Queue recovery runs explicitly at worker startup; creating a `JobQueue` handle must not recover in-flight work.
- Library, corrections, retranslation, history and glossary pages reach the worker through `UnitService` (`units.py`, in `RuntimeContext.units`) and the pure router `library_api.py`; `library.py` knows units and statuses, `rules.py` (pure) merges the glossary with episode corrections and the style layers and hashes them (a different hash than the stored `glossary_hash` means stale), `glossaries.py` (`Glossaries`) owns the glossaries in the database. `TranslationAttempt` takes the `Library` so a job is registered and prompted with its rules. Retranslation jobs are queue files with `trigger: retranslate` and `priority: 100`; `should_skip_job` lets them overwrite and `_ready_job_path` runs them first.

- Story memory (P4): `subcore.memory` is pure (facts, fold, render); `subserver/services/memory.py` (`StoryMemory`) decides which facts a unit sees, reads prerequisites inline, waits on gaps (`ContextGapError` → the queue defers the job) and says when a version is stale. "Facts of a unit" is always the newest stored facts for the current `EXTRACT_PROMPT_VERSION`, for building a bundle and for checking staleness alike; keep it that way. The attempt asks memory for sections only through `StoryMemory.plan`, and maps provider errors raised while extracting exactly as for translating. Memory is off unless `memory_enabled` or the series says `on`.

- Suggestions (P13): one table, one use case. `SuggestionService` (`suggestions.py`, in `RuntimeContext.suggestions`, routes in the pure `suggestion_api.py`) is the only place that stores a generator's proposals (`propose`), decides them (`accept`, `reject`, `undo`, `bulk`) and applies them; a generator hands it a list of `Proposal`s and has no review logic of its own, whatever its `source`. Accepting goes through `Glossaries.save_doc` (and `write_character` when a character carries its voice, one transaction) and counts the stale translations with `Library.impact_units`, the same count the Glossary page shows; it never retranslates. `auto_accept_*` goes through the same `accept`. `bootstrap.py` is the other P13 seam: `AutoRequest` and `CatalogView` both ask it whether a series is held back (`is_locked` is pure).

- Insights and the feedback loop (P15): `Metrics` (`metrics.py`) is the one place that works out the figures of FR-19.5. It rolls the raw records (`llm_calls`, `quality_signals`, `translation.finished` events) into `metrics_daily` (per UTC day, name and labels, rolled again from the last roll-up and never for a day the events clean-up has begun to prune) and the report only adds those rows up, so a figure outlives its events; a rate with nothing to divide by is `None`, never 0. A corrected cue is blamed on the prompt version of the job that wrote it (its signal carries the job). `FeedbackProposer` (`feedback.py`, `subcore.feedback` is the pure part) turns a swap of words repeated in three or more corrected cues into a `term` through `SuggestionService.propose` with `source = feedback`: no model call, no research `sources` (so `auto_accept_terms` never applies it), and it must never raise into a cue edit (`UnitService._after_edit`). A cue edit keeps the machine's text as `before_text` in its correction, inherited through later edits of the cue; only the golden set (`subcore.golden`, scored by `subcore compare --golden x.json`) reads corrections without it. Routes: `insight_api.py` (`/api/metrics`, `/api/series/{id}/golden`, in `RuntimeContext.insights`) and `POST /api/suggestions/from-edits`.

- The LLM judge (P15, FR-18.8): advice, never a verdict. `subcore.judge` is pure (the rubric, the request, the parse; which text is shown first is a fixed function of the cue number, `variant_is_a`, so neither side is always A; a model's `A`/`B` is mapped back to `variant`/`current`/`tie` and an entry that is not what was asked is dropped). `JudgeService` (`judge.py`, `UnitService.judge`) is the one place that queues (`request`, the interactive class, `estimate_only` for the price), runs (`run`, called by `JudgeJob` in `read_jobs.py` under `mapped_errors` and `JobProviders.for_task("judge")`, so `judge_model`, the day's quota, `max_calls_per_job` and Stop apply) and reads (`annotate`, laid over `UnitService.compare`). A verdict is a `judge` quality signal bound to the exact pair of texts it saw, the candidate version and `JUDGE_PROMPT_VERSION`; it is **never** an `ab` signal (`Metrics` reads only the admin's), never a cue edit and never starts a retranslation. Each batch is stored when it returns, so a stopped run loses nothing paid for. Off by default (`judge_enabled`); the Compare card and the route say so instead of spending. The runtime settings carry the switches of suggestions and of the judge (`SettingsService.settings`), so a switch turned off in the console reaches the running worker.

- Proposals from facts (P14): `subcore.suggest` is pure (candidates from facts and cues, then one `extract`-task call per kind that returns target-language forms; no timecode goes to the model) and `subserver/services/proposals.py` (`FactsProposer`, `SuggestionService.generator`) feeds the result to `SuggestionService.propose` (`facts`: address rules and terms; `memory`: characters) and never applies anything itself. `TranslationAttempt` calls `after_facts` once the job is settled, with the units `StoryMemory.plan(extracted=…)` collected; it only queues a `suggest` job for the series (`FactsProposer.request`, origin `facts`, the lowest class) and must never raise into the job, so the look for proposals spends its own turn and budget. A proposal from facts has no `sources`, so `auto_accept_terms` cannot apply it. What the inbox holds in any status, and what the model recently had no answer for (`suggestion_skips`, `SKIP_DAYS`, per prompt version), is taken out of the candidates *before* each kind's limit, never after it. `FactsProposer.run` stores each kind as soon as it returns and lets a provider error propagate typed, so a run is safe to repeat and loses nothing already paid for; a character is read only up to the episode where it qualified (a card applies to every episode: a unit never sees the facts of a later one) and a character that already has a card is not a candidate.

- Long work is a job (F7, D7): every task that spends model calls is a row of `jobs` and goes through the one queue, so the day's quota, `max_calls_per_day`, the breaker, Stop and a restart apply to all of it. `kind` is `publish` and `variant` (translate a subtitle: `TRANSLATING_KINDS`) or `extract` (the facts of one episode, key `extract:<unit_id>`, one job per episode so Stop works between episodes) or `suggest` (proposals for one series and language, key `suggest:<series>:<lang>`, at most three calls) or `judge` (the LLM judge on one candidate, key `judge:<unit>:<lang>:<version>`, calls of 30 cues each); `READING_KINDS` read and have no subtitle, no bundle and no strong model. `QueueWorker.run_job` runs a job by its kind through handlers `worker.py` registers (`register_handler`: `translate_job`, `ExtractJob`, `SuggestJob` and `JudgeJob` in `read_jobs.py`); a handler does its work and lets typed provider errors through `provider_guard.mapped_errors`, the one place that maps `QuotaExhausted`, `RateLimited`/`Unavailable`, `AuthError`, `ModelNotFound` and `TranslationError` to the queue's classes, and takes its providers from `provider_guard.JobProviders` (deadline, `max_calls_per_job`, `max_calls_per_day`, one provider per model). The admin's request is the interactive class and only queues (`POST …/context/extract`, `POST /api/suggestions/generate`: no synchronous path, no `background` flag; `estimate_only` stays synchronous because it spends nothing). Every reader of jobs says which kinds it means (`job_name`, `latest_for(kind=)`, `layer_report`, `catalog_view`, `_hard_job`, `estimate_retry`); a new kind must be added to that list with a test. There is no second background mechanism: a long wait that spends no model call (`sync_now`) wakes the existing loop instead.

Invariants:

- A unit never sees the facts of a later unit (story order is Bazarr's `(season, episode)`; season 0 sits outside the chain). Facts come from source subtitles, never from translations. A stale translation is flagged, never retranslated automatically.

- The catalog (P10, FR-14) is a cache with an age and never makes a job. `CatalogSync` applies a read of Bazarr only when it is whole and plausible: an error, a timeout, an empty answer or one that shrank by more than `catalog_shrink_guard` is set aside, the cache stays as it was and the state says why; nothing becomes "not missing" because Bazarr failed. Items are identified by Bazarr's own id (`kind` + `bazarr_id`), never by a path; a job finds its files again through `CatalogPaths.refresh` when it is claimed. The label of an (item, language) is derived on reading (`CatalogView`), never stored in a column. Jobs come from exactly two places: an admin's request (`JobRequests`, origin `manual`, interactive class) and the policy (`AutoRequest`, origin `policy`, automatic class, only after an accepted read; off by default; per series `on`/`off`; never an Ignored or Removed item, one with a job, one whose last finished job failed or was cancelled by the admin (only an admin's request retries it, D4; `JobStore.last_ended_state`), one outside `GST_ONLY_PATHS`, nor past `auto_request_daily_cap`, and `Requested.capped` counts only what that cap held back). **Sync now** only asks: `CatalogSync.request` wakes the background loop (`run_catalog_sync` in `worker.py`, the only caller of `sync_and_request`) and answers at once; `AutoRequest.run` is also guarded by a lock so two passes never add up past the cap; `accept_shrink` lets one read past the guard. Jobs are made only by `JobRequests` and the policy: there is no `/api/enqueue`. The bootstrap's first episodes are the first that still need a translation, plus the ones this worker already translated (`Store.translated_episodes`). A GET never writes (`GET /api/series/{id}/memory` makes no unit; the Context tab POSTs `…/memory/adopt` once); `catalog_apply` writes only rows that changed and a page of the Library reads its units and jobs once (`CatalogView.job_index`). `TranslationAttempt` reads the job's `origin`: only `manual` (or a retranslation) brings back a subtitle the admin removed. The script, `held`/`rejected` and `admission_mode` are gone; the importer settles an older queue once (held and the script's unapproved `pending` files → Missing, no job; rejected → Ignored, written before the row or folder that held it goes and kept for the next start-up when it cannot be written), idempotently.
- An existing target subtitle is never overwritten by an automatic job. Only an explicit retranslation, cue edit or revert replaces it, and each keeps the previous file as a version first. A result that cannot go on disk safely (the file appeared during the job, the base version moved, the source changed) is a `candidate` version; only "Use this version" publishes it. Publishing is announced before the rename and settled at start-up (`TranslationVersions.reconcile`).
- Only a missing language is translated: a sibling subtitle already in the target language (any name, `existing_target_subtitle` in `subtitles.py`) or Bazarr no longer listing it in `missing_subtitles` (`target_still_missing`) ends the job with no model call. Real-Bazarr trials run with `GST_ONLY_PATHS` set (see `docs/CONFIGURATION.md`) and `auto_request` on for one series at a time; never point the worker at a whole library without that.
- Two model layers: the light default model does the work; the strong model (`gst_fallback_model`) only takes hard jobs (`HardJobError`), outages and spent quota. Do not widen what escalates without looking at `model_layers`.
- A stored glossary that no longer reads stops the job; a translation never silently runs without it. A glossary, a style and a character card are saved only after they validate (`GlossaryError`/`StyleError`, a `ValueError` naming the offending path).
- Glossary, style and character cards (P12) are in the database (`glossaries`, `glossary_history`, `style_profiles`, `character_cards`); the `series/<key>/glossary.<lang>.yaml` files are read once at start-up by `Glossaries.import_files`, never written, and YAML is only the exchange format. `Glossaries` and `Styles` (`styles.py`) own the tables; `StyleService` (`style_service.py`, routes in `style_api.py`) is what the Style page calls. The style is laid in layers by `subcore.style.resolve_style` (pure): language < preset < series < episode < character card, and the glossary beats all of them in the prompt. The rules hash covers the stored layers and every card of the series (`StyleLayers.fingerprint`, empty parts left out so an episode with no style keeps its old hash), not the language layer (that is the prompt version) and **not few-shot examples**: a cue edit must never flag a series stale (ADR-14 point 9). A style change flags, never retranslates (FR-5.6).
- The trial of a style (`StyleService.preview`) writes nothing: no file, no version. A `variant` job (`trigger: variant`, kind `variant`) always ends as a `candidate` (`TranslationVersions.publish` never puts it on disk) and ignores an existing target; `skip_reason`, `process_job` and `worker.process_job`'s Bazarr refresh all treat it so. `translations.params_json` says how a version was made (`range`, `variant`); a retranslated range is still stamped with the hashes of the whole episode (FR-11.3.6).
- Gemini, TMDB, and Bazarr API keys are never logged or returned unmasked: the API gives only the last four characters (`last_chars` in `settings.py`). Everything written down passes the one filter in `redaction.py` (log formatter, events, prompt bodies, job error files); new text sinks use it, and a new secret kind is added there. Keys live in the SQLite `api_keys` table (P6) and the environment only seeds them on the first run: new code reads them through `SettingsService`, never from `os.environ`, a file or `config.json` (read once by the importer, never written). A backup holds no key unless a manual one asks (`include_keys`), a scheduled one never does, and a restore never touches the `auth` table. `subcore` receives a key only as an argument.
- Settings are in the `settings` table (DB > environment > default) and are live without a restart: the handler saves through `SettingsService`, which tells its subscribers (the worker's `apply_settings`) after every change. Process-level configuration (paths, port, console account; `SYSTEM_SETTING_KEYS` in `config.py`) comes from the environment only. A provider error that names a bad key (`AuthError`) marks that key `invalid` through `KeyedProvider`; one that names a bad model (`ModelNotFound`) is a Settings warning, never a key problem. Both are typed errors: nothing parses their text.
- Telemetry (events, call records, quality signals, prompt bodies; P5) is best effort: core code calls the `Telemetry` port (`telemetry.NULL` when none is wired), which never raises and never blocks. Never put a telemetry write inside a job's own transaction or let its failure change a job's outcome. Record a decision with a `reason` a person can read; subtitle text goes only in `quality_signals` and prompt bodies.
- Every HTTP request (static and `/api/*`) passes a session cookie or Basic Auth in `AuthGate` (`subserver/api/security.py`, an ASGI middleware that runs before any route, the static files included; the accounts are `subserver/services/auth.py`); the only exceptions are `GET /login` and `POST /api/auth/login`. The single account lives in the SQLite `auth` table as a scrypt hash, seeded from `CONSOLE_USER`/`CONSOLE_PASSWORD` on the first run (the stored account wins afterwards; `CONSOLE_PASSWORD_RESET=1` overwrites it). Passwords and session tokens are never logged, stored in config, or exposed through `RuntimeContext` or `/api/settings`; `CONSOLE_AUTH=off` is the only opt-out.
- A suggestion that was decided is kept (a few bytes) and never cleaned up: it is why the same entry is not proposed again (FR-11.1.4). "The same entry" is the **identity** of `suggestion_keys.py` (kind, name or pair, `from`; case and spacing folded; never the model's wording), stored in `suggestions.identity` and checked by `propose` and by `Store.suggestion_add` in its own transaction; the content fingerprint stays only as the unique key. Accepting is the only way a machine proposal reaches a glossary or a card, `auto_accept_*` included, and an accepted character is merged field by field into the card and glossary entry the admin already has (Undo restores them exactly); a `term` is applied by itself only with two independent sources, counted by `suggestions.source_host` (the registered domain, so another page, `www.` or language edition of one site is the same source), an address rule or a character only when its own switch is on (FR-4.4). Undo restores exactly what an accept replaced and refuses when the entry changed since, so a later edit is never overwritten. `auto_request` holds a series with nothing approved to its first `auto_request_bootstrap` episodes (`bootstrap.py`, FR-15.12); the admin's own request is never held.
- File clean-up (P9, FR-13) never touches a media folder: `Cleanup` (`cleanup.py`) deletes through the owners of what it deletes (`JobStore.delete_expired`, which refuses any state that is not finished, so open jobs are out of reach; `TranslationVersions.prune`, which deletes only inside `backups/subtitles/` and keeps the current version, the first one and the newest N; `Glossaries.prune_history` (earlier glossary states in the database; it never touches the current glossary)), and its temporary-file sweep skips every media root and the folder of every target subtitle, only listing what it finds there. It previews unless asked `dry_run: false`; `0` in a `retention_*` setting switches its group off. A version whose copy went is `pruned`: the line stays, `revert` and diff refuse it with the reason, and nothing may read its `stored_path` (cache lookups skip it). New data the worker makes for itself needs a cleanup rule here or a stated reason it does not.
- Bazarr and the worker must see identical media paths (`/media/...`).
